## 작업 배경

기존 AI 맵 생성 구조는 `FakeAiMapClient`가 prompt에 따라 고정 샘플 맵을 반환하고, `AiMapGenerator`가 이를 `AiMapLayoutParser`와 `MapLayoutValidator`를 통해 검증한 뒤 사용하는 구조였다.

다음 단계로 실제 AI 연동을 고려하면서 처음에는 Firebase Function과 OpenAI/Claude API를 사용하는 방향을 검토했다. 하지만 현재 프로젝트는 출시 목적이 아니라 포트폴리오/시연 목적이므로, API 비용과 키 관리 부담이 적은 로컬 LLM 방식인 Ollama를 우선 적용하기로 했다.

초기 목표는 다음과 같았다.

```text
Unity
-> Ollama
-> AI가 맵 JSON 생성
-> AiMapGenerateResponse
-> Parser
-> Validator
-> Preview
```

하지만 실제 테스트 과정에서 AI가 직접 `tiles` 배열이나 `tileRows`를 생성하는 방식은 안정성이 낮다는 것을 확인했다.

---

## IAiMapClient 비동기화

Ollama, OpenAI, Firebase Function 같은 외부 호출은 HTTP 요청 기반이다. 따라서 기존 동기식 `IAiMapClient.GenerateMap()` 구조를 비동기 방식으로 변경했다.

현재 인터페이스는 다음과 같다.

```csharp
public interface IAiMapClient
{
    Task<AiMapGenerateResponse> GenerateMapAsync(AiMapGenerateRequest request);
}
```

이에 맞춰 `FakeAiMapClient`는 `Task.FromResult`로 기존 샘플 응답을 반환하도록 수정했다.

`AiMapGenerator`에는 `GenerateAsync()`를 추가했다. 기존 `IMapGenerator.Generate()` 호환을 위해 동기 래퍼는 유지했지만, Ollama 같은 HTTP 기반 생성은 `GenerateAsync()` 경로로 호출하는 것이 좋다.

## Ollama 직접 맵 생성 방식의 한계

처음 `OllamaAiMapClient`는 AI에게 직접 맵 JSON을 생성하게 했다.

초기 출력 구조는 다음과 같았다.

```json
{
  "success": true,
  "errorMessage": "",
  "map": {
    "width": 17,
    "height": 11,
    "tiles": [],
    "player1Spawn": { "x": 3, "y": 5 },
    "player2Spawn": { "x": 13, "y": 5 }
  }
}
```

하지만 작은 로컬 모델에서는 다음 문제가 반복적으로 발생했다.

```text
tiles 개수가 width * height와 맞지 않음
tileRows 줄 수가 height와 맞지 않음
각 row 길이가 width와 맞지 않음
스폰 위치가 Floor가 아님
스폰 위가 Empty가 아님
Floor 개수가 부족함
프롬프트 의도와 결과 맵이 어긋남
```

예를 들어 17x11 맵은 187개의 tile이 필요하지만, AI가 227개의 tile을 반환하는 경우가 있었다. 이후 `tileRows` 방식으로 바꿨지만, row 개수나 row 길이가 틀리는 문제가 계속 발생했다.

이를 보정하기 위해 row 길이 보정, 스폰 보정, 기본 발판 보정, 낙사 edge 보정 등을 추가했지만, 보정이 많아질수록 사용자의 prompt 의미가 사라지는 문제가 생겼다.

결론적으로 AI에게 최종 타일맵 생성을 직접 맡기는 방식은 현재 로컬 LLM과 프로젝트 목표에는 맞지 않는다고 판단했다.

## Intent 기반 구조로 전환

AI가 맵 타일을 직접 생성하지 않고, 맵 생성 의도만 반환하도록 구조를 변경했다.

변경된 방향은 다음과 같다.

```text
사용자 입력 또는 선택 테마
-> Ollama가 의도/옵션 JSON 생성
-> Unity의 Builder가 실제 맵 생성
-> Parser
-> Validator
-> fallback
```

이 방식에서는 AI가 다음과 같은 데이터를 반환한다.

```json
{
  "theme": "bridge",
  "bridgeCount": 3,
  "spawnDistance": "far",
  "dangerLevel": "medium",
  "wallDensity": "none",
  "platformScale": "medium",
  "seed": 12345
}
```

AI가 관여하는 영역은 다음으로 제한했다.

```text
theme
bridgeCount
spawnDistance
dangerLevel
wallDensity
platformScale
seed
```

실제 `tiles` 생성은 Unity 코드가 담당한다.

## 자유 프롬프트 대신 테마 enum 선택

자유 프롬프트는 결과 예측이 어렵고, 사용자의 기대와 실제 맵이 어긋나는 문제가 컸다.

따라서 최종적으로는 Inspector에서 테마를 enum으로 선택하고, AI는 선택된 테마 안에서 옵션만 결정하도록 구조를 바꾸었다.

추가한 enum은 다음과 같다.

```csharp
public enum AiMapTheme
{
    Bridge,
    Island,
    Warehouse
}
```

`MapPreviewSpawner`에는 다음 필드가 추가되었다.

```csharp
[SerializeField] private AiMapTheme aiMapTheme = AiMapTheme.Bridge;
[SerializeField] private string aiStyleHint = "";
```

`aiStyleHint`는 자유 프롬프트가 아니라 선택된 테마 안에서 옵션을 조정하기 위한 보조 힌트로 사용한다.

예를 들어 `AiMapTheme.Bridge`를 선택하면 Ollama는 반드시 `theme = "bridge"`를 유지해야 하며, `bridgeCount`, `dangerLevel`, `wallDensity`, `platformScale`, `seed` 같은 옵션만 선택한다.

## 테마별 Builder 구조

확장성을 위해 단일 `switch` 구조 대신 인터페이스 기반 테마 빌더 구조로 변경했다.

공통 인터페이스는 다음과 같다.

```csharp
public interface IAiThemeMapBuilder
{
    string Theme { get; }
    AiMapLayoutDto Build(AiMapIntentDto intent, AiMapGenerateRequest request);
}
```

현재 구현된 테마 빌더는 다음과 같다.

```text
BridgeThemeMapBuilder
IslandThemeMapBuilder
WarehouseThemeMapBuilder
```

`IntentBasedAiMapBuilder`는 직접 맵을 생성하지 않고, intent의 `theme` 값을 보고 적절한 `IAiThemeMapBuilder`를 선택하는 라우터 역할만 담당한다.

```text
IntentBasedAiMapBuilder
-> BridgeThemeMapBuilder
-> IslandThemeMapBuilder
-> WarehouseThemeMapBuilder
```

나중에 `Bus`, `Factory`, `Tower` 같은 테마를 추가하려면 새 Builder 클래스를 만들고 라우터에 등록하면 된다.

---

## 공통 유틸 분리

테마별 빌더에서 반복되는 타일 조작 코드는 `AiThemeMapBuilderUtility`로 분리했다.

현재 주요 역할은 다음과 같다.

```text
CreateEmptyMap
Fill
FillRect
SetTile
GetTile
EnsureStandable
EnsurePath
EnsureSpawnRules
ApplyDanger
ApplyWalls
CreateRandom
Normalize
```

이를 통해 각 테마 빌더는 맵의 큰 형태를 만드는 데 집중하고, 스폰 보정이나 위험 요소 배치 같은 공통 처리는 유틸에서 처리한다.

## Seed 기반 랜덤 변형

같은 테마를 선택해도 매번 같은 맵이 나오지 않도록 `seed` 기반 랜덤 변형을 도입했다.

`AiMapIntentDto`에는 다음 필드가 있다.

```csharp
public int seed;
```

Ollama가 seed를 반환하지 않거나 예시값을 그대로 반환할 경우, `OllamaAiMapClient`에서 `Environment.TickCount`를 사용해 seed를 보정한다.

각 Builder와 공통 유틸은 다음 방식으로 랜덤 객체를 만든다.

```csharp
System.Random random = AiThemeMapBuilderUtility.CreateRandom(intent, salt);
```

이 구조의 장점은 다음과 같다.

```text
같은 seed -> 같은 맵 생성 가능
다른 seed -> 같은 테마 안에서도 다른 변형 생성
멀티플레이 동기화 시 seed 기반 재현 가능성 확보
```

현재 랜덤 변형이 적용되는 요소는 다음과 같다.

```text
Bridge
- 섬 크기 일부 변화
- 다리 위치 일부 변화

Island
- 중앙 섬 위치 일부 변화
- 연결 발판 위치 일부 변화

Warehouse
- 발판 크기 일부 변화
- 엄폐물 위치 일부 변화

공통
- 낙사 구멍 위치 일부 변화
- 벽 위치 일부 변화
```

## 현재 시연 흐름

`MapPreviewSpawner`에서 다음 설정으로 AI 테마 맵을 확인할 수 있다.

```text
Preview Map Source = Ollama
Ai Map Theme = Bridge / Island / Warehouse
Ai Style Hint = 선택 사항
```

실행 흐름은 다음과 같다.

```text
MapPreviewSpawner
-> AiMapGenerateRequest 생성
-> OllamaAiMapClient.GenerateMapAsync
-> Ollama가 선택 테마 안의 옵션 intent 생성
-> IntentBasedAiMapBuilder
-> 테마별 Builder
-> AiMapGenerateResponse
-> AiMapGenerator
-> AiMapLayoutParser
-> MapLayoutValidator
-> 실패 시 DefaultMapGenerator fallback
```

## 현재 한계

현재 구조는 모든 자유 프롬프트를 처리하는 방식이 아니다.

대신 지원 가능한 테마를 제한하고, 그 안에서 AI가 옵션을 고르는 방식이다.

지원하지 않는 요청은 가장 가까운 테마로 처리하거나 기본값으로 fallback한다.

현재 지원 테마는 다음 세 가지다.

```text
Bridge
Island
Warehouse
```

따라서 `버스맵`, `공장맵`, `타워맵` 같은 요청을 완전히 반영하려면 별도의 테마 빌더를 추가해야 한다.

이 방식은 AI의 자유도를 줄이는 대신 다음 장점을 가진다.

```text
맵 검증 통과율이 높아짐
프롬프트와 결과가 크게 어긋나는 문제 감소
테마별 품질 관리 가능
확장 시 새 Builder만 추가하면 됨
멀티플레이에서 동일 맵 재현 가능성이 높아짐
```

## 정리

이번 작업을 통해 AI 맵 생성 구조는 다음 방향으로 정리되었다.

```text
AI가 최종 맵을 직접 생성하지 않는다.
AI는 선택된 테마 안에서 생성 옵션만 결정한다.
실제 타일맵은 테마별 Builder가 생성한다.
Parser와 Validator는 기존대로 최종 안전성을 보장한다.
실패 시 DefaultMapGenerator로 fallback한다.
```

최종적으로 이 구조는 포트폴리오에서 다음 포인트를 보여줄 수 있다.

```text
로컬 LLM 연동
비동기 AI 클라이언트 구조
AI 출력 신뢰 최소화
Intent 기반 생성 구조
테마별 전략 패턴
Validator 기반 안전성 확보
Fallback 처리
Seed 기반 랜덤 변형
```

AI 맵 생성 기능은 1차 구현 단계로 마무리하고, 이후 작업에서는 멀티플레이에서 Host가 생성한 최종 맵을 모든 클라이언트가 동일하게 사용하는 동기화 구조로 이어갈 수 있다.

## 작업 배경

Gun Push Arena의 핵심 컨셉은 플레이어가 총알의 넉백으로 상대를 직접 처치하는 것이 아니라, 상대를 발판 밖으로 밀어내 낙사시키는 2D 아레나 게임이다.

최종 목표는 Claude/GPT 같은 AI가 2D 맵 설계 데이터를 생성하고, Unity가 그 데이터를 검증한 뒤 실제 맵으로 생성하는 흐름이다. 다만 처음부터 AI API, 네트워크, 로비 연결까지 동시에 구현하면 범위가 커지므로, 5월 14일 작업에서는 AI 없이 로컬에서 맵 데이터를 만들고 검증하는 기초 구조부터 준비했다.

이번 작업의 핵심 방향은 다음과 같다.

```text
MapLayoutData 생성
→ 랜덤 맵 또는 기본 맵 생성
→ MapLayoutValidator로 검증
→ 실패 시 기본 맵 사용
→ 테스트용 프리뷰로 화면 확인
```

아직 실제 게임용 발판/낙사 중심 생성 규칙으로 변경하지는 않았다. 현재 랜덤 맵은 테스트용으로, 내부 바닥을 넓게 깔고 일부 벽을 배치하는 형태다.

---

## 작업 목표

이번 작업의 목표는 다음과 같았다.

1. AI 응답과 로컬 랜덤 생성기가 공통으로 사용할 맵 데이터 구조를 만든다.
2. 1차원 배열과 width/height 기반으로 타일 좌표를 관리한다.
3. AI 응답 실패 또는 검증 실패 시 사용할 기본 맵 생성기를 만든다.
4. 맵 크기, 타일 배열, 스폰 위치, 스폰 간 거리, 바닥 개수, 스폰 간 경로를 검증하는 구조를 만든다.
5. 검증 기준값은 ScriptableObject로 분리해 Inspector에서 조절할 수 있게 한다.
6. 실제 Tilemap으로 넘어가기 전, 테스트용 프리뷰 스포너로 맵이 화면에 찍히는지 확인한다.

## 맵 데이터 구조

### MapTileType

맵 타일은 현재 세 종류로 나누었다.

```csharp
public enum MapTileType
{
    Empty = 0,
    Floor = 1,
    Wall = 2
}
```

각 의미는 다음과 같다.

```text
Empty
→ 바닥이 없는 공간
→ 이후 낙사 영역으로 사용 예정

Floor
→ 플레이어가 설 수 있는 발판

Wall
→ 이동 불가능한 장애물
```

현재 테스트 맵에서는 `Wall`을 랜덤 장애물로 사용하고 있지만, 게임 컨셉상 최종 맵은 벽보다 발판과 낙사 공간이 더 중요하다. 따라서 이후 `Wall` 사용량을 줄이거나 선택적 장애물로만 사용하는 방향이 적합하다.

### MapLayoutData

런타임 생성형 맵은 `MapLayoutData`로 표현한다.

```text
Width
Height
Tiles
Player1Spawn
Player2Spawn
```

타일 배열은 2차원 배열이 아니라 1차원 배열로 관리한다.

```csharp
index = y * Width + x
```

이 방식을 선택한 이유는 다음과 같다.

```text
JSON 직렬화가 쉽다.
AI 응답 구조로 사용하기 쉽다.
네트워크 동기화 시 배열 형태로 전달하기 쉽다.
width/height만 있으면 2D 좌표로 복원할 수 있다.
```

좌표 접근용 메서드도 추가했다.

```text
GetIndex(x, y)
IsInBounds(x, y)
GetTile(x, y)
```

`GetIndex`에서는 좌표가 맵 범위 밖이면 예외를 던지도록 했다. 개발 중 잘못된 좌표 접근을 빨리 확인하기 위한 목적이다.

## 랜덤 맵 생성기

`RandomMapGenerator`는 현재 테스트용 랜덤 맵을 생성한다.

현재 흐름은 다음과 같다.

```text
1. Width 17, Height 11 크기의 맵 생성
2. 전체 타일을 Empty로 초기화
3. 바깥 한 칸을 제외한 내부 영역을 Floor로 채움
4. 일정 확률로 Wall 배치
5. 플레이어 스폰 주변 3x3 영역을 Floor로 보장
6. 완성된 MapLayoutData 반환
```

현재 스폰 위치는 다음과 같이 좌우로 배치했다.

```text
Player1Spawn = (3, Height / 2)
Player2Spawn = (Width - 4, Height / 2)
```

스폰 주변은 `EnsureSafeSpawnArea`에서 3x3 영역을 Floor로 덮어 안전하게 만들었다. 이 처리는 플레이어가 벽 안이나 낙사 공간에서 시작하는 문제를 막기 위한 안전장치다.

현재 랜덤 생성기는 테스트용으로는 정상 동작하지만, 게임 컨셉에는 아직 완전히 맞지 않는다. 지금은 넓은 사각형 바닥 위에 벽이 놓이는 구조라서, 총으로 상대를 밀어 떨어뜨리는 아레나보다는 일반 장애물 맵에 가깝다.

## 기본 맵 생성기

`DefaultMapGenerator`는 생성 실패 또는 검증 실패 시 사용할 보험용 맵 생성기다.

역할은 다음과 같다.

```text
랜덤 생성 실패
AI JSON 파싱 실패
AI 응답 검증 실패
예상하지 못한 맵 데이터 오류
```

이런 상황에서 게임이 멈추지 않도록, 무조건 사용할 수 있는 기본 `MapLayoutData`를 생성한다.

현재 기본 맵은 다음 흐름으로 생성된다.

```text
1. Width 17, Height 11 크기 생성
2. 전체 Empty 초기화
3. 내부 영역 Floor 생성
4. 중앙 주변에 고정 Wall 몇 개 배치
5. 두 플레이어 스폰 주변 3x3을 Floor로 보장
```

기본 맵은 재미있는 맵을 만드는 것이 목적이 아니라, 시연 중 실패 상황에서도 게임이 계속 진행되도록 하는 안정성 확보가 목적이다.

## 맵 검증 설정

검증 기준은 코드 상수로 고정하지 않고 `MapValidationSettings` ScriptableObject로 분리했다.

현재 설정값은 다음과 같다.

```text
minWidth
maxWidth
minHeight
maxHeight
minFloorCount
minSpawnDistance
requireSpawnPath
```

ScriptableObject로 분리한 이유는 다음과 같다.

```text
맵 밸런싱 값을 Inspector에서 조절할 수 있다.
AI 맵 생성 실험 중 기준값을 빠르게 바꿀 수 있다.
작은 맵, 큰 맵, 테스트용 설정을 별도 에셋으로 만들 수 있다.
코드를 수정하지 않고 검증 기준을 조정할 수 있다.
```

`requireSpawnPath`는 두 플레이어 스폰 사이에 길이 이어져 있어야 하는지를 결정한다. 현재 검증 방식은 Floor만 따라 BFS로 이동 가능한지 확인한다.

점프가 들어가더라도 초기 프로토타입에서는 이 검사가 필요하다고 판단했다. 최소한 걸어서도 연결된 안전한 맵을 허용하면, 시연 중 플레이어들이 서로 만날 수 없는 맵이 생성되는 위험을 줄일 수 있기 때문이다.

## 맵 검증기

`MapLayoutValidator`는 랜덤 맵, 기본 맵, 이후 AI 맵을 모두 같은 기준으로 검증하기 위한 클래스다.

현재 검증 흐름은 다음과 같다.

```text
1. MapValidationSettings 존재 여부 확인
2. MapLayoutData null 여부 확인
3. Width 범위 검사
4. Height 범위 검사
5. Tiles null 여부 검사
6. Tiles.Length == Width * Height 검사
7. Player1Spawn 유효성 검사
8. Player2Spawn 유효성 검사
9. 두 스폰 간 거리 검사
10. 최소 Floor 개수 검사
11. requireSpawnPath가 true이면 두 스폰 간 Floor 경로 검사
```

스폰 검사는 다음 두 가지를 확인한다.

```text
스폰 좌표가 맵 범위 안에 있는가
스폰 위치의 타일이 Floor인가
```

바닥 개수 검사는 `CountFloorTiles`로 처리한다. 전체 타일 배열을 순회하면서 `MapTileType.Floor` 개수를 세고, 설정된 최소 개수보다 적으면 실패 처리한다.

스폰 간 연결 검사는 BFS로 처리한다.

```text
Player1Spawn에서 시작
상하좌우 Floor 타일만 탐색
Player2Spawn에 도달하면 성공
끝까지 도달하지 못하면 실패
```

이 검사는 AI가 막힌 맵이나 분리된 섬 맵을 반환했을 때 게임이 멈추거나 플레이 불가능해지는 문제를 막기 위한 기본 안전장치다.

## 테스트용 맵 프리뷰

실제 Tilemap 구현 전, `MapPreviewSpawner`를 만들어 맵 데이터가 화면에 찍히는지 확인했다.

현재 역할은 다음과 같다.

```text
RandomMapGenerator로 맵 생성
MapLayoutValidator로 검증
검증 실패 시 DefaultMapGenerator 사용
MapLayoutData의 Tiles를 순회
Floor, Wall, Spawn marker를 화면에 표시
```

처음에는 `GameObject.CreatePrimitive(PrimitiveType.Quad)`로 표시했지만, URP/2D 환경에서 색상이 모두 흰색으로 보이는 문제가 있었다. 이후 테스트 프리뷰는 `SpriteRenderer` 방식으로 변경했다.

또한 처음에는 맵이 `(0, 0)`부터 오른쪽 위로 생성되어 카메라 중심과 맞지 않았다. 이를 해결하기 위해 맵 좌표를 중앙 정렬하도록 보정했다.

현재 프리뷰 표시 방식은 다음과 같다.

```text
Floor
→ 회색

Wall
→ 검정색

Player1Spawn
→ 청록색

Player2Spawn
→ 자홍색
```

렌더링 겹침을 줄이기 위해 z 위치도 분리했다.

```text
Floor: z = 0
Wall: z = -0.1
Spawn marker: z = -0.2
```

현재 맵이 실제 화면에 생성되는 것까지 확인했다.

## 확인된 이슈

### 1. 현재 랜덤 맵은 게임 컨셉에 맞는 최종 형태가 아님

현재 랜덤 맵은 넓은 바닥 위에 벽을 랜덤 배치하는 구조다.

```text
전체 Empty
→ 내부 전체 Floor
→ 일부 Wall 랜덤 배치
```

하지만 Gun Push Arena는 상대를 발판 밖으로 밀어내는 게임이므로, 최종 맵은 벽 중심이 아니라 발판/낙사 중심이어야 한다.

이후 변경 방향은 다음과 같다.

```text
전체 Empty
→ 중앙에 기본 발판 생성
→ 발판 모양을 랜덤하게 확장하거나 깎음
→ 맵 내부에도 Empty를 만들어 낙사 위험 생성
→ Wall은 없거나 적게 사용
→ 스폰 주변은 안전하게 Floor 보장
```

이 작업은 아직 진행하지 않았다.

### 2. 낙사형 맵 검증 규칙이 아직 부족함

현재 검증기는 일반적인 플레이 가능 여부를 확인한다. 하지만 낙사형 아레나에 필요한 검증은 추가되어야 한다.

추가 후보는 다음과 같다.

```text
Empty 타일 최소 개수
Floor와 Empty가 맞닿는 가장자리 개수
Wall 최대 개수
스폰 주변 3x3 Floor 보장 여부
낙사 위험이 충분한지 여부
```

특히 `Floor`와 `Empty`가 맞닿는 가장자리 수는 중요하다. 이 값이 적으면 플레이어를 밀어도 떨어뜨릴 공간이 부족해진다.

### 3. 테스트 프리뷰는 임시 구현임

`MapPreviewSpawner`는 맵 데이터 확인용 임시 코드다.

정식 구현에서는 Tilemap 기반의 `TilemapMapBuilder` 또는 실제 게임용 맵 빌더로 교체해야 한다.

테스트 프리뷰에서 확인한 내용은 다음과 같다.

```text
MapLayoutData가 정상 생성된다.
검증 실패 시 기본 맵으로 대체할 수 있다.
Floor, Wall, Spawn 위치가 화면에 표시된다.
카메라 중심과 맵 중심을 맞춰야 한다.
프리뷰 렌더링은 SpriteRenderer 방식이 더 안정적이다.
```

## 현재 구조 요약

현재 맵 생성 기초 구조는 다음과 같다.

```text
MapTileType
→ Empty, Floor, Wall 정의

MapLayoutData
→ width/height + 1차원 타일 배열 기반 런타임 맵 데이터

RandomMapGenerator
→ 테스트용 랜덤 맵 생성

DefaultMapGenerator
→ 실패 시 사용할 안전한 기본 맵 생성

MapValidationSettings
→ 검증 기준값을 ScriptableObject로 관리

MapLayoutValidator
→ 맵 크기, 타일 배열, 스폰, 바닥 수, 경로 검증

MapPreviewSpawner
→ 테스트용 시각화
```

이 구조 덕분에 이후 AI 맵 생성이 들어와도 다음 흐름을 유지할 수 있다.

```text
AI 응답 JSON 파싱
→ MapLayoutData 생성
→ MapLayoutValidator 검증
→ 성공 시 AI 맵 사용
→ 실패 시 DefaultMapGenerator 사용
```

## 작업 배경

이전 단계까지는 Relay + Netcode 연결 이후 Host가 `TestPlayer` NetworkObject를 각 슬롯 위치에 스폰하고, 모든 클라이언트가 같은 `Map1`과 같은 `finalMap`을 로드하는 것까지 확인했다.

이번 작업의 목표는 단순 스폰 확인을 넘어서 실제 게임 플레이가 가능한 1차 루프를 만드는 것이었다.

```text
입장
-> 2D 플랫폼 맵 생성
-> 플레이어 이동 / 점프
-> 발사체 발사
-> 피격 넉백
-> 낙사 시 라이프 감소
-> 한 명만 생존하면 승패 표시
-> 로비 복귀
```

Firestore는 기존 방향 그대로 로비/방/맵/relayJoinCode 공유까지만 사용하고, 실제 플레이 중 위치, 발사체, 충돌, 승패 판정은 Netcode 서버 권한 구조로 처리하도록 유지했다.

## 맵 방향 전환

초기 `finalMap`은 `Floor`, `Wall` 타일을 정사각형 셀 단위로 생성하는 구조였다. 이 방식은 격자형 탑다운 맵에는 맞지만, 현재 목표인 Brawlhalla 스타일의 플랫폼 전투와는 맞지 않았다.

따라서 `MapLayoutData`와 `MapTileType` 구조는 유지하되, 해석 방식을 변경했다.

```text
Floor
-> 캐릭터가 밟는 얇은 가로 플랫폼

Wall
-> 막히는 장애물 또는 커버 타일

Empty
-> 낙사 가능한 빈 공간
```

즉 Firestore에 저장되는 `finalMap` 구조는 그대로 두고, 게임 씬에서 Floor를 "셀 덩어리"가 아니라 "플랫폼 라인"으로 렌더링하고 충돌시키는 방식으로 바꿨다.

## GameMapSpawner 변경

`GameMapSpawner`는 이제 Floor 타일을 개별 정사각형으로 만들지 않고, 인접한 Floor를 가로 run 단위로 병합한다.

```text
연속된 Floor 셀 탐색
-> 하나의 플랫폼 GameObject 생성
-> 얇은 사각형 시각 요소 생성
-> EdgeCollider2D를 플랫폼 상단에만 생성
```

상단 EdgeCollider만 사용하는 이유는 플레이어가 플랫폼 옆면에 닿았을 때 입력 방향으로 계속 붙어 있는 현상을 줄이기 위해서다. 기존 BoxCollider2D 기반 플랫폼은 옆면도 충돌면이 되기 때문에, 캐릭터가 점프 중 옆면에 닿고 A/D를 계속 누르면 벽에 달라붙는 느낌이 강했다.

현재 구조는 다음과 같다.

```text
Floor platform
-> 상단 EdgeCollider2D
-> 마찰 0 PhysicsMaterial2D

Wall tile
-> BoxCollider2D
-> 마찰 0 PhysicsMaterial2D
```

또한 맵 하단 기준으로 `DeathY`를 계산해, 플레이어가 일정 높이 아래로 떨어지면 서버에서 낙사를 처리할 수 있게 했다.

## 기본 맵과 AI 테마 맵 변경

`DefaultMapGenerator`는 안정적인 테스트를 위해 얇은 메인 플랫폼과 보조 플랫폼 2~3개를 만드는 구조로 변경했다.

기본 방향은 다음과 같다.

```text
중앙/좌우 플랫폼
상단 보조 플랫폼
하단 보조 플랫폼
양쪽 플레이어 스폰 지점
낙사 가능한 빈 공간
```

AI 테마 빌더도 같은 방향으로 수정했다.

```text
Bridge
-> 좌우 섬과 중앙 연결 플랫폼 중심

Island
-> 분리된 섬과 높낮이가 다른 보조 플랫폼 중심

Warehouse
-> 긴 메인 플랫폼과 커버성 Wall 일부 포함
```

이전에는 `EnsureSpawnRules`가 스폰 사이를 강제로 Floor로 연결하면서 테마별 차이가 많이 사라졌기 때문에, 자동 연결 보정을 줄이고 플랫폼 run 수를 기준으로 검증하도록 조정했다.

## 로비 맵 미리보기 변경

`LobbyMapPreviewView`도 게임 씬과 같은 해석을 따르도록 변경했다.

기존에는 모든 Floor/Wall을 셀 단위 사각형으로 표시했다. 현재는 Floor를 가로 플랫폼처럼 보이도록 연속 구간 단위로 렌더링한다.

```text
Floor
-> 얇은 가로 플랫폼 미리보기

Wall
-> 개별 사각형 장애물 미리보기
```

이로 인해 로비에서 보는 맵과 실제 게임 씬의 플랫폼 구조가 더 비슷하게 보이게 되었다.

## PlayerController 2D 플랫폼 이동

`PlayerController`는 기존 3D XZ 이동 전제를 버리고 2D 플랫폼 이동 기준으로 정리했다.

현재 이동 흐름은 다음과 같다.

```text
Owner client
-> Move / Jump / Fire 입력 읽기
-> ServerRpc로 입력 요청

Server
-> Rigidbody2D velocity 결정
-> 점프 횟수, 낙사, 발사 요청 처리
-> NetworkTransform / NetworkRigidbody2D로 위치 동기화
```

중요한 전제는 Owner만 입력을 읽고, 최종 위치와 물리 결과는 Host/Server가 결정한다는 점이다.

---

## 2단 점프

점프는 1차 점프 + 공중 1회 점프가 가능한 2단 점프로 변경했다.

```text
maxJumpCount = 2
remainingJumpCount = maxJumpCount

착지 상태가 확인되면 remainingJumpCount 초기화
점프 입력이 들어오면 remainingJumpCount 감소
```

`IsGrounded()`는 플레이어 콜라이더 하단 기준으로 BoxCast를 사용한다. 착지 상태이고 아래 방향 속도가 거의 0에 가까울 때 점프 횟수를 회복한다.

기존 프리팹에 낮은 `jumpForce`나 높은 `gravityScale`이 직렬화되어 있을 수 있으므로, 런타임에서 최소/최대 값을 보정했다.

```text
jumpForce 최소 12
gravityScale 최대 2.5
```

## 낙사와 라이프

플레이어는 서버 권한 `Lives` NetworkVariable을 가진다.

```text
기본 Lives = 3
transform.position.y < deathY
-> 서버에서 라이프 감소
-> 남은 라이프가 있으면 스폰 위치로 리스폰
-> 0이면 탈락 상태
```

`NetworkPlayerSpawner`는 플레이어를 스폰한 뒤 `InitializeRoundState(spawnPosition, deathY)`를 호출해 각 플레이어의 리스폰 위치와 낙사 기준선을 초기화한다.

테스트 결과 3번 낙사 후 더 이상 리스폰되지 않고 탈락 상태가 되는 것을 확인했다.

## 발사 입력과 바라보는 방향

Input System에 `Fire` 액션을 추가하고, 키보드 `J`에 바인딩했다.

발사 방향은 마우스 조준 없이 A/D 이동 방향으로 결정한다.

```text
A 입력
-> facing left

D 입력
-> facing right

Fire 입력
-> 현재 facing 방향으로 발사
```

`PlayerController`는 서버에서 `serverFacingDirection`을 저장하고, `FireServerRpc()`가 호출되면 해당 방향으로 발사체를 생성한다.

## NetworkProjectile

`NetworkProjectile`은 발사체 전용 NetworkBehaviour다.

현재 역할은 다음과 같다.

```text
서버에서만 이동
Rigidbody2D Kinematic 사용
NetworkTransform으로 위치 동기화
수명 종료 시 despawn
자기 자신과 충돌하면 무시
다른 대상과 충돌하면 despawn
```

발사체 프리팹은 Unity Editor에서 별도로 만들고 NetworkManager의 Network Prefabs에 등록해야 한다.

필요한 구성은 다음과 같다.

```text
Projectile Prefab
-> NetworkObject
-> NetworkTransform
-> NetworkProjectile
-> Rigidbody2D
-> Collider2D
-> 시각용 SpriteRenderer 또는 Shape
```

## 넉백

발사체가 다른 플레이어에 닿으면 서버에서 `PlayerController.ApplyProjectileHit()`을 호출한다.

넉백은 단순히 `AddForce`만 사용하지 않았다. 현재 이동 로직은 매 FixedUpdate마다 좌우 속도를 입력 기반으로 다시 결정하기 때문에, 일반적인 힘 적용만으로는 넉백이 바로 덮어써질 수 있다.

따라서 피격 직후 짧은 시간 동안 좌우 이동 입력이 넉백 속도를 덮어쓰지 않게 했다.

```text
hitKnockback = (8, 4)
knockbackControlLock = 0.18초

피격
-> x 방향 넉백 속도 적용
-> y 방향 최소 상승 속도 적용
-> 짧은 시간 이동 입력 덮어쓰기 방지
```

이 구조로 발사체 피격 후 플레이어가 뒤로 밀리고, 플랫폼 밖으로 떨어지면 기존 낙사/라이프 로직으로 이어진다.

## 단판 게임 종료 판정

단판 MVP를 위해 `GameRoundManager`를 추가했다.

`GameRoundManager`는 Host/Server에서만 라운드 상태를 감시한다.

```text
Host가 플레이어 스폰 완료
-> GameRoundManager.StartWatching(expectedPlayerCount)
-> PlayerController 목록 확인
-> Lives > 0인 플레이어 수 계산
-> 생존자가 1명만 남으면 승자 결정
-> ClientRpc로 모든 클라이언트에 결과 전달
```

승패 판정은 Firestore를 사용하지 않고 Netcode 서버 상태만 기준으로 한다.

## 게임 결과 UI MVP 구조

처음에는 코드에서 런타임으로 `Canvas`와 결과 패널을 생성했다. 하지만 UGUI 버튼 입력은 씬의 `EventSystem`, `InputSystemUIInputModule`, Canvas 설정에 의존하므로, 프로젝트의 MVP 패턴과도 맞는 씬 배치형 UI로 변경했다.

최종 구조는 다음과 같다.

```text
GameResultUIView
-> UGUI 참조 보관
-> ShowWin()
-> ShowLose()
-> Hide()
-> ReturnLobbyClicked 이벤트 발행

GameResultPresenter
-> 결과 표시 결정
-> ReturnLobbyClicked 처리
-> NetworkManager.Shutdown()
-> GameSessionContext.ClearSession()
-> LobbyScene 로드
```

`PlayerController.AnnounceGameResultClientRpc()`는 이제 `GameResultPresenter.ShowResult(winnerClientId)`를 호출한다.

Unity Editor에서는 `Map1`에 다음 구성이 필요하다.

```text
Canvas
-> GameResultPanel
   -> ResultText
   -> ReturnLobbyButton

EventSystem
-> InputSystemUIInputModule

GameResultUIView
GameResultPresenter
```

`GameResultPanel`은 처음에는 비활성화해두고, 승패 결과가 들어오면 View가 활성화한다.

## 정리

이번 작업으로 `Gun Push Arena`는 단순한 온라인 스폰 테스트에서 2D 플랫폼 전투 MVP로 넘어왔다.

핵심 변화는 다음과 같다.

```text
격자형 맵 해석
-> 플랫폼 전투용 맵 해석

단순 TestPlayer 스폰
-> 이동/2단 점프/발사/넉백/낙사/라이프 처리

플레이 상태 없음
-> 단판 승패 판정과 결과 UI 흐름

런타임 임시 UI
-> Map1 UGUI + MVP 패턴 기반 결과 UI
```

Firestore는 여전히 로비와 게임 시작 전 공유 상태까지만 담당하고, 실제 게임 플레이 상태는 Netcode 서버 권한 흐름에서 처리한다. 이 방향은 이후 총알 판정, 넉백 밸런스, 승패 조건 확장에도 그대로 유지한다.
